§1

Purpose & Scope

The Excel importer exists for one purpose: bringing an already-resolved or already-in-progress finding from a bank record predating this system into it, in bulk. It is not a faster way to register a brand-new finding — a genuinely new finding is always entered one at a time through Register Finding, where it goes through District Review and HO Review exactly as the workflow requires.

Every row you import is fast-forwarded straight to the status you declare — through the same underlying mechanism a live approval, rectification, or transfer uses — and is permanently marked in its history as a historical import, never as a live decision. This keeps the audit trail honest: anyone opening the finding later can see at a glance that it was backfilled, and by whom.

§4

Status Guide

Pick the status that matches the finding's real, current state in the old process you're backfilling from — not a status you'd like it to reach later. All three skip District Review and HO Review entirely; that step already happened, historically.

SENT_TO_BRANCH_MANAGER

Approved. Nothing fixed yet.

  • The finding cleared review and was sent to the branch, but no correction has been recorded at all.
  • Ignores Rectified Cases/Amount and Transferred To Period Code even if you fill them in.
  • Lands the finding exactly where a freshly-approved live finding would sit.
Status SENT_TO_BRANCH_MANAGER
Rectified Cases (blank)
Transferred To… (blank)
TRANSFERRED

Moved forward, still outstanding.

  • The period it started in closed out with a balance still unresolved, so it was carried into a later, still-open period.
  • Requires Transferred To Period Code — a real, open period, later than Reporting Period Code.
  • Rectified Cases/Amount are optional: how much (if anything) was fixed before it moved. Zero is fine; the full amount is not — that would mean nothing was left to transfer.
  • Whatever portion you do declare rectified is also treated as already closed — no controller has to re-close a fact you're attesting already happened.
Status TRANSFERRED
Rectified Cases 1 of 3
Transferred To… 2026-10
CLOSED

Fully resolved.

  • Every case, and the full amount, was corrected and formally closed in the old process.
  • No Rectified Cases/Amount column needed — the importer fills the full case count and amount in for you.
  • Nothing is left outstanding; there is nothing further to do on this finding.

Rectified Cases (not needed)

§5

How Validation Works

Four rules apply to the whole file, not just one row at a time — understanding them explains most of what the result screen will show you.

1

The whole file succeeds or none of it does. Every row is checked first. If even one row has a real error, nothing in the file is imported — fix every row shown and re-upload the whole thing. A row that's merely a duplicate doesn't block the rest; only a genuine error does.

2

Duplicates are judged on data, not wording. Branch, period, source, department, category, finding date, operation area, irregularity type, currency, amount, and case count together decide a match — Title and Description can differ freely and it's still flagged the same finding.

3

Reference numbers are never yours to set. The system always generates them from the branch and the finding's original Reporting Period Code — even for a Transferred row, whose reference reflects where it started, not where it ended up.

4

Finding Date drives the finding's recorded age. Case-age figures on every dashboard are measured from it, not from today's import — so a genuinely old backlog item reads as old, not as brand new.

§6

Before You Upload

✓

Download a fresh template each session. Required columns and valid codes can change; an old file's header still parses, but its Reference Data sheet may not reflect today's lists.

✓

Codes are exact, not close. A district/branch/source/department/category/currency/risk/priority/area/type must match the Reference Data sheet's spelling exactly.

✓

Amount and Number of Cases are the finding's whole totals — not whatever's still outstanding. Outstanding is derived automatically from Status and Rectified Cases/Amount.

✓

Transferred needs two different, real periods — its own origin period, and a currently-open destination period that comes after it in time.

✓

No itemized case amounts. If your legacy record has a genuine per-case dollar breakdown, that detail can't be preserved through import — only the combined total can.

✓

No Root Cause column. Add it afterward from the finding's own detail page if it's needed.

✓

This is not a live-review shortcut. A finding that genuinely needs District/HO review belongs on Register Finding, one at a time — never in this file.

✓

Read every row of the result, not just the totals. On a rejected file, the same row-by-row table tells you exactly which rows to fix before your next upload.
