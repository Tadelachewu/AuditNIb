# Phase 6 — Findings Registration & Full Workflow

Every phase before this built the *foundation* Findings would eventually
sit on: organizations and users (Phase 1), dynamic roles and permissions
(Phase 2/5), full CRUD with confirmed risky actions (Phase 3), and a Branch
dashboard deliberately built with "no data yet" placeholders exactly where
Finding data would eventually go (Phase 4). This phase is that data: the
`Finding` entity, the complete BRD workflow state machine from
registration through district review, HO review, rectification, and
verified closure, and wiring the Branch dashboard's placeholders up to the
real numbers they were always structured to hold.

Scope, decided with the user before writing code: the **Transfer Engine**
(BRD §3.7 — carrying an unresolved balance to a new reporting period) is
deferred to its own future phase; `TRANSFERRED` is a real status in the
type but unreachable this pass. **Evidence** is a plain text note field,
not a file upload — there's no object storage in the app (BRD §3.12 itself
flags this as an open infrastructure decision). **Threaded comments**
(BRD §3.11) are deferred; the mandatory reason already required on
reject/return covers reviewer communication for now.

## 1. The state machine, literally

master.txt §11 and the roadmap doc's own clean summary ("DRAFT → SUBMITTED
→ DISTRICT_REVIEW → (APPROVED/REJECTED/RETURNED) → HO_REVIEW → HO_APPROVED
→ SENT_TO_BRANCH_MANAGER → PARTIALLY_RECTIFIED/RECTIFIED/TRANSFERRED →
CLOSED") name 13 states. All 13 are kept as real, persisted
`FindingStatus` values (`src/types/index.ts`) — including the ones that
only exist for a moment, like `SUBMITTED` and `DISTRICT_APPROVED`. Rather
than skip those as redundant, each "pass-through" is a second, automatic
transition fired immediately after the triggering action, in the same
request:

```
DRAFT --[Submit]--> SUBMITTED --[auto]--> DISTRICT_REVIEW
DISTRICT_REVIEW --[District Approve]--> DISTRICT_APPROVED --[auto]--> HO_REVIEW
HO_REVIEW --[HO Approve]--> HO_APPROVED --[auto]--> SENT_TO_BRANCH_MANAGER
```

This was a deliberate choice over silently merging those states away: it
means the full 13-state vocabulary from the BRD is genuinely reachable and
inspectable in the transition history (verified directly — see §6), not
just a subset an implementer decided was "enough." `src/lib/findings.ts`'s
`submitFinding()`/`districtApproveFinding()`/`hoApproveFinding()` are the
three functions that pair a real action with its automatic follow-on, each
built on the one primitive everything else in this phase also uses:

```ts
transitionFinding(db, finding, { toStatus, action, userId, userName, reason? })
```

— which mirrors `src/lib/audit.ts`'s `appendAuditLog` pattern exactly: it
updates `finding.status`, pushes a `FindingTransition` row (the finding's
own history), and appends a normal `AuditLogEntry` (`entityType: "Finding"`)
so the same event is visible in both the finding's timeline and the
bank-wide audit log, satisfying the BRD's "full transition history stored
(who, when, from-state, to-state, reason)" (plan doc §3.4) without a
second, parallel bookkeeping system.

`RETURNED` and `DRAFT` are the only editable states (plan doc §3.3), and
`RECTIFIED → CLOSED` is deliberately not self-service by whoever recorded
the rectification — that's the BRD §3.6 "verification" gate, implemented
as its own permission (`findings.close`) rather than folded into
`findings.rectify`.

## 2. Data model

Three new collections in `Database` (`src/types/index.ts`):

- **`Finding`** — the fields BRD §6 lists (reference, source, period,
  district/branch, date, operation area, irregularity type, classified
  case, amount+currency, case count, risk level, description,
  recommendation, evidence note, status), plus `rectifiedCases`/
  `rectifiedAmount` as running cumulative totals. Outstanding is *always*
  computed as `caseCount - rectifiedCases` / `amount - rectifiedAmount` on
  read, never stored — the same "never let a derived number drift" rule
  Phase 1 already applied to branch manager/controller lookups.
- **`FindingTransition`** — one row per state change (including the
  automatic pass-throughs above), the finding's own audit trail.
- **`RectificationEntry`** — one row per rectification event, its *own*
  amount (not cumulative — the cumulative total lives on `Finding`, kept
  in lockstep by the same `updateDb()` call that appends the entry).

`reference` is generated by `nextFindingReference()`
(`<branchCode>-<periodCode>-<seq>`, e.g. `B001-2026-08-001`), sequenced per
branch+period — verified to produce `B001-2026-08-001` then
`B001-2026-08-002` for two findings registered against the same branch and
period in the smoke test (§6).

## 3. Permissions: one `findings` page, nine actions

Following the standing rule from PHASE5.md, `findings` is a
`PAGE_REGISTRY` entry (`src/lib/permissions/registry.ts`) with
`view`/`create`/`edit`/`delete` plus five workflow-specific actions added
to the `PermissionAction` union the same ad hoc way `activate`/`lock`/
`manage` were before: `submit`, `district-review`, `ho-review`, `rectify`,
`close`. Each maps to exactly one stage of the state machine, so a role
can hold, say, `rectify` without `close` — matching BRD §3.6's split
between "record the correction" (Branch Manager) and "verify and close it"
(District/HO Controller) as two different capabilities, not one.

Every seeded role's defaults (extending PHASE5.md's table, each traced to
a specific icfms.txt line) were verified directly against a reseeded
server:

| Role | New findings permissions | Verified count includes |
|---|---|---|
| `BRANCH_CONTROLLER` | view, create, edit, delete, submit, rectify | "Register/Edit draft/Submit findings... Verify rectifications" |
| `BRANCH_MANAGER` | view, rectify | "Record corrective actions... Enter rectified case counts" |
| `DISTRICT_CONTROLLER` | view, district-review, close | "Review branch submissions... Approve or return"; closure is their §3.6 verification duty |
| `DISTRICT_DIRECTOR` | view only | icfms.txt is explicit: "Cannot modify findings or scores" |
| `HO_CONTROLLER` | view, create, ho-review, close | "Register Internal Audit findings"; second-approval stage |
| `EXECUTIVE_READONLY`, `ADMIN` | automatic (all `.view` / everything) | unchanged mechanism from Phase 2/5 |

`District Director`'s permission set was specifically re-verified live: a
`POST .../district-review` call authenticated as `district.director`
returned `403 Forbidden` before it ever reached the finding, because they
simply don't hold `findings.district-review` — the BRD's "cannot modify"
restriction is enforced by *absence of a grant*, not a special-cased check
in the route.

## 4. Org-scope enforcement — `src/lib/findings-scope.ts`

Centralized in two functions everything else calls, rather than
reimplemented per route, because the BRD repeats this requirement in
several places ("Filters must never bypass organizational scope", "UI
scope is not a security boundary; server/API must enforce access"):

```ts
isFindingInScope(session, finding)   // BANK: true; DISTRICT: districtId match; BRANCH: branchId match
findingsInScope(db, session)         // every finding the caller may see at all
assertFindingInScope(session, finding) // null, or an error string for a 403
```

Every mutating route in `src/app/api/findings/` calls
`assertFindingInScope` before touching the record; every list view
(`GET /api/findings`, the `/findings` page itself) starts from
`findingsInScope` and only ever narrows further with query filters, never
widens past it — the same principle the `FilterBar`'s `fixedDistrict`/
`fixedBranch` props already encoded in Phase 4, now backed by something
real to enforce.

This was verified as a genuine security boundary, not just a UI
convenience: a District Controller from `district-2` calling
`POST /api/findings/<id>/district-review` against a `district-1` finding
got `403` with *"This finding is outside your organizational scope"* — and
that same finding was absent from their own `GET /api/findings` list
entirely (`0 findings visible`), confirming the scope check applies to
reads as well as writes.

## 5. Routes and pages

`src/app/api/findings/` — `route.ts` (list + create), `[id]/route.ts`
(get/edit/delete), and one route per workflow action
(`submit`, `district-review`, `ho-review`, `rectify`, `close`). Every
handler: `requirePermission("findings.<action>")` first, then
`assertFindingInScope`, matching the shape of every admin route built in
earlier phases. `rectify` independently checks cases and amount against
what's still outstanding — plan doc §3.5's own acceptance example (3
cases/45,000 → 1 case/10,000 rectified, 2 cases/35,000 outstanding) is
exactly this rule, and is the literal scenario reproduced in the verified
run below.

`src/app/(app)/findings/` — `page.tsx` (list, the `FilterBar` from Phase 4
now actually driving results via `FindingsFilterBar`'s URL-param sync,
plus a permission-driven "My Queue" toggle), `new/page.tsx` (the
registration form covering every BRD §3.3 field), `[id]/page.tsx` (detail:
full record, the rectification ledger, the transition-history timeline,
and only the action buttons the current session's permissions *and* the
finding's current status both allow). `src/proxy.ts` gates the whole
`/findings/*` route behind `findings.view` the same way `/admin/<page>` is
gated; the action-level checks live in each API route as usual.

Every workflow action that can't be undone or that changes what's visible
to someone else — Reject, Return, Close, Delete — goes through the
`useConfirm()` dialog from Phase 3, with Reject/Return requiring the
typed reason (`needsReason: true`) the same way Reporting Periods'
lock/unlock already does.

## 6. Verified end-to-end (live, not just reviewed)

Ran the BRD's own acceptance path against a running server, one seeded
user per stage, no shortcuts:

1. **`branch.controller`** registers a 3-case / ETB 45,000 "Other Case"
   finding as `DRAFT`. Confirmed absent from `district.controller`'s
   `DISTRICT_REVIEW` queue at this point.
2. **Submit** → status `DISTRICT_REVIEW`. Now present in the district
   queue; still absent from `ho.controller`'s `HO_REVIEW` queue.
3. **`district.director`** (view-only) attempts to approve it →
   `403 Forbidden`, never reaches the finding.
4. **`district.controller`** approves → status `HO_REVIEW`, confirmed via
   the transition history: `DISTRICT_REVIEW → DISTRICT_APPROVED → HO_REVIEW`
   as two logged rows, not one.
5. **`ho.controller`** approves → status `SENT_TO_BRANCH_MANAGER`.
6. **`branch.manager`** attempts to rectify 4 cases against 3 outstanding
   → `400`, rejected before any state changes.
7. **`branch.manager`** records **1 case / ETB 10,000** → status
   `PARTIALLY_RECTIFIED`, outstanding correctly `2 cases / ETB 35,000` —
   the plan doc's own example, reproduced exactly.
8. **`branch.manager`** records the remaining **2 cases / ETB 35,000** →
   status `RECTIFIED`.
9. **`branch.manager`** attempts to close it → `403` (no `findings.close`
   permission — closure isn't self-service, per §3.6).
10. **`district.controller`** closes → status `CLOSED`.
11. Any further edit attempt on the closed finding → `409 Only draft or
    returned findings can be edited`.

Screenshots confirmed the same story renders correctly through the actual
UI: the Branch Dashboard's KPI row, Other Case Summary, and Category
Totals table — all `"--"` placeholders in Phase 4 — now show real numbers
(`Total Findings: 2`, `Performance: 100.0%`, `Other Case: 3/3/0`); the
Findings list shows both test findings with correct status badges; the
registration form renders every field with district/branch correctly
locked for a branch-scoped role; and the closed finding's detail page
renders the complete 9-row transition history plus the two-entry
rectification ledger. Zero browser console errors across all four screens.

## 7. What's still deferred

Transfer Engine (`TRANSFERRED` unreachable), real file/evidence upload,
threaded comments, in-app/email notifications (BRD §3.11/§3.12), and
configurable per-source routing rules (every source follows the same
uniform pipeline this phase, rather than the BRD's "configurable routing
rules per finding source" nuance). District, HO, and Executive dashboards
are still the Phase 4 placeholders — wiring them up to this phase's real
Finding data the way the Branch dashboard now is remains future work.
